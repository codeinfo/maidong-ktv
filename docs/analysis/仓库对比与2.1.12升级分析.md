# 仓库对比与「当前分支升级到 2.1.12」分析

> 生成时间：2026-11-15　|　分析对象：E:\ktv　|　当前分支：android-4.4.4 @ 74abbcf（versionName 1.1.0）

## 一、先说结论

1. **两个仓库不是同一个 git 历史。** GitHub `codeinfo/maidong-ktv` 与 Gitee `yangyachao-X/maidong-ktv` 没有共享提交，抽样 7 个 Gitee 提交做祖先检测全部为「否」，Gitee 侧 1.2.2/1.2.3 两个提交的说明本身就是 `merge: accept local changes over remote (unrelated histories)`。所以**不存在「pull 一下就跟上 2.1.12」这条路**，只能换基线 + 重放补丁。
2. **当前分支的定位是「1.1.0 + Android 4.4 兼容改造」**，而 **2.1.12 的定位是「minSdk 21 + Media3/FFmpeg 播放栈 + iGeba/OpenList 音源」**。两者在技术底座上正面冲突：2.1.12 依赖的 `androidx.media3` 只支持 API 21+，`coreLibraryDesugaring` 只补 Java API、补不了平台 API。
3. 因此升级前必须先做一个决策：**目标盒子是否还有 Android 4.4 设备**。
   - 没有 → 直接换基线到 2.1.12，工作量主要在工具链与打包（约 0.5～1 人日）。
   - 有 → 2.1.12 装不上，只能「双线并行」，或者自行把 minSdk 改回 19 并重做播放栈（高风险，不建议）。
4. 两个**立刻会挡路的硬缺口**（已在本机核实）：**NDK 27.0.12077973 未安装**、**`ktv_keystore.jks` 在本机不存在**（`E:\ktv\ktv_keystore.jks` 与 `E:\ktv_keystore.jks` 都没有）。

## 四、当前分支的「4.4 改造」到底是什么（升级时要保住的东西）

工作区未提交改动 10 个文件 +281/−89，另有新增 `TlsCompat.kt`、两份真机测试报告、真机测试截图目录（现已整理进 `docs/assets/screenshots/`）。其技术内容：

| 改动 | 目的 | 在 2.1.12 里的处境 |
|---|---|---|
| `TlsCompat.kt`：给 API<21 的 `HttpsURLConnection` 显式开 TLS1.2/1.1/1.0 | 4.4 默认不启 TLS1.2，CDN 握手失败 | 只有把 minSdk 改回 19 才有意义；若走 iGeba 纯 HTTP 源，主要场景可不要 |
| `gradle.properties` 的 `DATABASE_MANIFEST_URL/MIRRORS` 改为 ghfast/jsDelivr | 国内直连 raw.githubusercontent 不可用 | **2.1.12 没有这些 buildConfig 注入了**，机制整体消失 |
| 新增 `MEDIA_BASE_URL`（`app/build.gradle`） | 4.4 打不开 wb66.cn 的 TLS1.2+ 链接，改指 HTTP 镜像 | 2.1.12 音源换 iGeba（`http://app.ige8.net/cloud.php`、`/telnet.php`，纯 HTTP），此限制基本被绕开 |
| `DatabaseBootstrapper.kt` +86：可达镜像 + 分片断点续传 | 曲库下载健壮性 | 对应 2.1.12 的 `IgebaCatalogBootstrapper` / `CatalogAssets` / `LegacyStorageUpgrade`，**逻辑需重写不能平移** |
| `player/KtvVideoView.kt` +125 | 4.4 播放/渲染兼容 | 2.1.12 已拆成 `KtvPlaybackEngine` 三件套，改动需在新引擎上重做 |
| `MainActivity` / `QuickSearchAdapter` / `SongListAdapter` / `activity_main.xml` | 焦点、列表、布局适配 | 2.1.12 已有 `TvListNavigation` / `TvFocusStyler` / `TvUiScale` 体系，需与新体系合并 |
| `SongOkDownloadManager.kt` | 下载细节 | 同名文件被 2.1.12 完全重写，需对照新实现重估 |

## 五、升级到 2.1.12 要做的事（按顺序）

### 步骤 0：决策 —— 是否必须保留 Android 4.4

- `androidx.media3:media3-exoplayer:1.7.1` 最低 API 21；`coreLibraryDesugaring`（desugar_jdk_libs 2.1.5）只补 Java 语言 API，不补 `MediaCodec`/`Surface` 等平台能力。
- 若强行把 2.1.12 的 minSdk 改回 19：Media3 渲染路径、`KtvRenderersFactory`、NDK 层 `ffmpeg_player.cpp` 的 Surface 输出都要在 4.4 上验证，成本高且上游不再回归 4.4。**不建议**。
- 建议：**4.4 线保留为独立分支照常发版；主线切 2.1.12 面向 Android 5.0+ 盒子**。

### 步骤 1：保存现场（必须先做）

当前有 10 个未提交修改 + 未跟踪文件，且 `Untracked` 里有两份真机测试报告要留档。

```powershell
cd E:\ktv
git switch -c wip/android-4.4.4-$(Get-Date -Format yyyyMMdd)   # 或先 git stash -u
git add -A; git commit -m "wip: 4.4 compat (catalog mirrors, TLS, media mirror, player tweaks)"
git checkout -b patch/4.4-compat                              # 起点，后续用来做补丁集
```
另外把 `安卓4.4.2-真机测试报告.md`、`安卓4.4.4-模拟器测试报告.md` 与测试截图备份到版本库外的目录（它们不在任何分支里）。注：2026-11-15 已统一整理到 `docs/`（`reports/` 与 `assets/screenshots/`），并纳入 git。

### 步骤 2：修复 promisor 指向（否则切分支就报错）

本仓库是 `blob:none` 部分克隆 + `sparse-checkout`（排除 `database_publish`），**promisor 远程 `origin` 指向已失效的 `ghfast.top`**，任何缺失 blob 的读取都会报：

```
fatal: unable to access 'https://ghfast.top/...': Could not connect to server
fatal: could not fetch <sha> from promisor remote
```

（本次分析中已实际触发过。）两种处理方式，任选：

```powershell
# 方式 A：把 origin 直连 GitHub（推荐，已验证可连通）
git remote set-url origin https://github.com/codeinfo/maidong-ktv.git
# 方式 B：只在本条命令里临时覆盖，不改配置
git -c remote.origin.url=https://github.com/codeinfo/maidong-ktv.git status
```
另外建议关掉 `database_publish` 的 sparse 规则（2.1.12 已无该目录）：
```powershell
git sparse-checkout set /*
```

### 步骤 3：切到 2.1.12 基线

```powershell
git fetch upstream --tags          # 已完成，本地已有 1.0…2.1.12 全部 tag
git switch -c v2.1.12-base 2.1.12   # 2.1.12 = 860f0b5（feature/igeba-media 线）
```
注意：**不要从 `upstream/master` 取版本**，master 落后。

### 步骤 5：源码层「整树替换」，别做局部 merge

因为历史无关、结构大改，正确的做法是**以 2.1.12 的树为准**，把：

- 本地独有的 4 个文件（`MuseDatabase` / `SongApiClient` / `TsDecryptor` / `DatabaseBootstrapper`）→ 删除；
- 本地独有资产（`app/libs/original-ijk-runtime.jar`、`app/src/main/jniLibs/armeabi-v7a/*.so` 4 个、`database_publish/database/*` 95 个、`drawable/ic_loading.png`、`androidTest` 的 4.4 测试）→ 按 2.1.12 的形态处理（2.1.12 已删除或替换）；
- 31 个同名文件（`app/build.gradle`、`MainActivity.kt`、`Layout`、`res` …）→ 直接采用 2.1.12 版本，**不要保留 1.1.0 的写法**；
- 依赖改动：去掉 `okdownload` 与 `files('libs/original-ijk-runtime.jar')`，加上 `media3-exoplayer`、`nextlib-media3ext`、`desugar_jdk_libs`。

如果走「保留 4.4」路线，则把 `patch/4.4-compat` 的 10 个文件按上面的**映射表**逐条重写到 2.1.12 对应模块（`KtvVideoView` → `KtvPlaybackEngine` 系列是最大的一块）。

## 六、三种路线与建议

| 路线 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A. 双线并行（推荐）** | `android-4.4.4`（1.1.0）继续维护；新建 `v2.1.12-base` 出正式线，面向 5.0+ 盒子 | 两条线各自发版，补丁可能要重写两遍 | 现场还有 4.4 盒子，且新盒子是 5.0+ |
| **B. 单线切 2.1.12** | 放弃 4.4，整树换基线 | 工具链 0.5～1 人日；4.4 老设备全部淘汰 | 现场设备已统一到 5.0+ |
| **C. 强行保 4.4** | 在 2.1.12 上把 minSdk 改回 19，重做播放与 TLS | 5～10 人日且成功率低，Media3/NDK 在 4.4 上无上游保障 | 不建议 |

## 七、风险与未决项

1. **keystore 缺失**：拿不到原 `ktv_keystore.jks` 就无法做出「可覆盖升级」的包，只能卸载重装，用户已下载歌曲与曲库状态会丢（2.1.12 有 `LegacyStorageUpgrade`/`PersonalMediaMigration`，但覆盖安装才用得上）。
2. **iGeba 依赖第三方 HTTP 服务**（`app.ige8.net`）：纯 HTTP 无 TLS 问题（对 4.4 友好），但可用性、账号授权与带宽不受控；这也是 2.1.12 要「歌源地址恢复」的原因。
3. **`origin` 镜像已失效**：`ghfast.top` 连不上，直连 `github.com` 正常。建议把 origin 改成直连，否则每次 fetch/lazy-fetch 都会失败。
4. **APK 体积与 16KB page**：新增 `arm64-v8a`、24 个 ffmpeg so、`-Wl,-z,max-page-size=16384`，release 包会明显变大；老盒子若只支持 32 位，靠 v7a 仍可跑。
5. **Kotlin 2.1.21 + AGP 8.10.1**：Kotlin 2.x 的编译行为与 1.9.22 有差异（`kotlinOptions` 与新 DSL、增量编译缓存），首次全量编译可能暴露 1.1.0 代码里的隐性警告/错误。
6. 本次分析中 **未执行任何构建**（只做只读比对与远程 fetch），也未改动工作区文件；上述「需要做什么」是按构建配置与源码结构推导，实际编译错误要在步骤 6 里暴露后再补。
