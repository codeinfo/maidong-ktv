## 2. 曲库为什么不走应用内下载

真机首次启动（推库之前）实测报错并停在初始化页：

```
曲库初始化失败：javax.net.ssl.SSLProtocolException: SSL handshake aborted:
ssl=0x782afeb8: Failure in SSL library, usually a protocol error
error:14077102:SSL routines:SSL23_GET_SERVER_HELLO:unsupported protocol
```

即 **Android 4.4 的 OpenSSL 与 `ghfast.top` 的 TLS 配置握手失败**，应用内的 969 MB 分片下载在本机根本起不来。证据截图：`../assets/screenshots/真机测试/08-应用首屏.png`（内容为横屏，查看需旋转 270°）。

因此本轮改为**主机侧下载 + adb push 预置**，真机只承担 USB 传输：

1. 主机按 `gradle.properties` 的清单地址拉 93 个分片（8 线程，被源站限流后降到 4 线程重试补齐），拼装成 `muse.db`；
2. 校验：大小 **969,072,640 B**，sha256 `592ca5c6…3394` 与清单一致；
3. `adb push` 到 `/storage/sdcard0/MaidongKTV/database/muse.db`（5.6 MB/s，165 s）后设备侧 `md5sum` 与主机一致（`38d5164b…86e6`）。

启动逻辑是 `if (!library.muse.open()) 才下载`（`MainActivity` §416-425、`MuseDatabase.open()` OPEN_READONLY），所以预置后**首屏直接进主页，完全没有触发下载**。

| songs | **647,820** |
| singers | **133,874** |
| song_singer_relations | **719,049** |
| playlist_songs | 43,906 |
| playlists | 277 |

## 7. 结论

- 4.4.4 分支的 APK 在 **ARM 真机（nubia NX507J / Android 4.4.2 / v7a）可安装、可启动**，预置曲库后**跳过下载直接进主页**，数据库（64.78 万首 / 13.39 万歌手）可被应用打开。
- **模拟器报告里唯一未覆盖的 ARM + IJK 路径，本轮通过**：原生库正常加载，音频解码、渲染、结束、评分、入历史全链路跑通。
- 真机（640dp 宽）暴露两个**只在窄 dp 宽度下才出现**的布局缺陷：列表行文字 0 宽、拼音键盘行高 7 px，两者都会让「选歌 / 搜索」在真机上不可用，建议优先修。
- 4.4 设备的曲库下载路径（TLS 握手）本身不可用，现场部署需预置 `muse.db`；预置后务必加 `.nomedia`，否则 MediaScanner 会把整机拖死。

## 9. 媒体源调整与 TS 播放验证

### 9.1 内置媒体源为什么在 4.4 上不可用

`SongApiClient` 走 `http://gz.ac16.vip` 取签名地址（明文 HTTP，设备可达 61 ms），返回的是：

```
{"msg":"SUCCESS","data":"https:\/\/wb66.cn\/f\/d\/7b7c9\/10188555.ts","code":200}
```

三个问题叠加：
1. `wb66.cn` 只提供 **HTTPS**，其 TLS 配置在 Android 4.4 的默认 SSLSocket（不启用 TLS1.2）下握手失败；
2. 该地址在本机（TLS1.2/1.3 客户端）也连不上，说明链路本身就不可用；
3. 授权接口返回 `end_date: 2026-10-05`（已过期），两首不同的歌返回的是**同一个占位文件** `10188555.ts`。

### 9.2 改动

| 文件 | 改动 |
| --- | --- |
| `gradle.properties` / `app/build.gradle` | 新增 `MEDIA_BASE_URL`（BuildConfig 字段）。非空时下载地址按 `<base>/<filename>` 拼接；留空则回退内置签名接口 |
| `SongOkDownloadManager.kt` | `buildDownloadUrl` 优先使用 `MEDIA_BASE_URL`，绕开签名接口 |
| 新增 `TlsCompat.kt` | API<21 时给 `HttpsURLConnection` 换装显式开启 TLS1.2/1.1/1.0 的 SSLSocketFactory，解决「只支持 TLS1.2+ 的源」在 4.4 上的握手失败 |
| `SongApiClient.kt`、`DatabaseBootstrapper.kt` | 发起 HTTPS 前调用 `TlsCompat.install()` |

这样两种部署都能用：有可用镜像时配 `MEDIA_BASE_URL` 走 HTTP；想继续用内置接口时，TLS 兼容也把 4.4 的握手问题一并解决。

### 9.3 实测（真实 TS 视频）

- 主机起 `python -m http.server 8000` 提供一个真实 HLS 分片（H.264 + AAC，6,291,456 B），按库里的文件名 `7009126.ts`（恋人）与 `7351965.ts`（一样的月光）暴露给设备；
- 真机点「恋人(HD)」→ 下载成功：`/storage/sdcard0/MaidongKTV/video/cloud-song/7009126.ts`，6,291,456 B；
- 下载完成即自动播放：`/status` → `{"playing":true,"current":"恋人(HD)  -  李荣浩"}`，画面出现 HLS 测试图与时间码 `00:00:07:27`（见 `../assets/screenshots/真机测试/30-TS播放.png`），说明 **IJK 在 ARM 真机上解码 TS 的 H.264 视频 + 音频**；
- 播放结束评分 76 分并进历史（`score: "76 分  恋人(HD)  -  李荣浩"`，`historySize=3`）。

日志里 TS 切片边缘有 `Invalid timestamps` / `PES packet size mismatch` 警告，因为验证用的文件是从整段流里按字节切出来的片段（首尾不完整），完整文件不会有这类告警。

### 9.4 注意

- 当前 `MEDIA_BASE_URL` 指向本机测试源 `http://192.168.31.10:8000`，**生产部署要改回真实镜像地址或留空**（留空则走内置接口 + TLS 兼容）。
- 测试用的 HTTP 服务已停止，需要复测时在该目录重新 `python -m http.server 8000 --bind 0.0.0.0` 即可。
